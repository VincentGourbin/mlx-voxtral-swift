## Objectif
En mode `--trace` seulement, chaque frame TTS émet deux spans, « LLM i/n » (pas du transformeur sémantique) et
« FM i/n » (flow matching et tête acoustique), séparés par une barrière `eval` propre à ce mode ; `bench tts --trace`
rapporte la part de chacun. Le chemin streaming émet les phases « Semantic Code Generation » et « Codec Decode »
comme le batch. Hors `--trace`, rien ne change.

**Porte** : `bench tts --trace` sur tts-4b-4bit, tts-4b-6bit et tts-4b-mlx, texte court, `neutral_female`, graine 1,
batch : deux spans par frame, et une ligne `GPUPHASE` (ou champ de la ligne de diagnostic) par sous-étape avec sa durée
totale ; somme LLM + FM = durée des pas ±2 % ; parts LLM / FM consignées pour les trois packs dans
`docs/knowledge/benchmarks/m3max-tts-baseline-2026-10.md` ; `bench tts --streaming --trace` émet les phases
« Semantic Code Generation » et « Codec Decode » (aucune aujourd'hui) ; hors `--trace` : `out_sha256` identique et
`step_ms_p50` ±3 % (A/B/B/A, A = commit parent, tts-4b-6bit court, un processus par passe, `--warmup 1 --cooldown
120`) ; les sections « Gain attendu » de K-39, K-44, K-48 et K-57 notent la part mesurée du FM.

Si la barrière `eval` du mode trace ne peut pas être isolée du chemin normal : fiche `blocked` avec la mesure du coût.
